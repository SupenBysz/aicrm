# 多配色外观主题需求与迭代方案

日期：2026-10-29。状态：已进入源码实现；第 14 节为实施锁定，实际验证范围见实施与验证记录。

基线：`332fefc3c0d1950f494aef0c4c631a7620b78313`。本文依据当前工作空间源码梳理，不代表线上已具备本文设计的能力。

## 1. 目标与需求来源

将现有固定的亮色、暗色扩展为多套配色主题，每套配色均有完整亮暗版本。用户可以独立选择配色与明暗模式，系统各页面、插件和桌面外壳保持一致。

用户补充要求：本模块的设置项加入“系统配置”的 Tabs。按此要求新增独立“外观主题”页签，作为完整设置入口；顶部外观按钮提供个人快捷切换。

核心验收结果：

1. 亮暗模式和配色主题独立设置，支持跟随系统明暗。
2. 主题覆盖完整界面，不局限于按钮主色。
3. 切换立即生效，刷新后保留，登录后可恢复账号偏好。
4. 不卸载页面、不丢表单和滚动位置、不重建或隐藏 WebView。
5. 保留当前经典金外观，旧用户升级后无强制视觉变化。
6. 平台默认与个人选择明确分开，不能将个人操作误保存为全局配置。

## 3. 范围与首期产品选择

### 3.1 模式与主题

| 维度 | 首期建议 | 说明 |
| --- | --- | --- |
| 外观模式 | 亮色、暗色、跟随系统 | system 是持久化选项，最终 resolvedMode 只有 light/dark |
| 配色主题 | 经典金、商务蓝、翡翠绿 | 推荐首批三套，共六种实际视觉组合；具体颜色在实施中出样验收 |
| 后续扩展 | 雅致紫、中性灰等 | 增加主题配置即可，不增加独立业务判断 |
| 默认值 | 经典金＋跟随系统 | 既有显式 light/dark 选择保留 |

主题涵盖页面背景、导航、顶栏、容器、文字、边框、主色、交互状态、阴影和滚动条。成功、警告、错误、信息状态另设语义颜色，不随主色简单替换。

### 3.2 本轮包含

主题基础设施、三套配色及亮暗版本、系统配置页签、顶部个人快捷设置、平台默认、账号偏好、本地缓存与旧配置迁移、公共组件和现有插件适配、品牌预览及桌面外壳适配。

### 3.3 本轮不包含

用户任意输入 CSS/脚本、在线主题设计器、自定义上传主题包、机构级强制主题策略、按业务页面分别保存主题、改造外部网站内容配色、修改业务数据或菜单结构。

机构品牌 Logo、字体、AI 后缀开关继续按现有品牌规则工作；不因个人切换主题改变机构品牌配置。

## 4. 设置入口与交互

### 4.1 系统配置新增“外观主题”页签

入口：系统设置 → 系统配置 → 外观主题。建议排列在“基础信息”之后、“参数配置”之前。URL 使用现有系统配置路由加 `?tab=appearance`，实施时复用当前工作区路由前缀。

页签内部分两块，避免混淆保存范围：

| 区块 | 字段与操作 | 生效范围 |
| --- | --- | --- |
| 我的外观 | 配色主题、外观模式、跟随平台默认、恢复跟随平台 | 当前账号；与顶部快捷设置共用状态和接口 |
| 平台默认 | 默认配色、默认外观模式、亮暗预览、保存平台默认、恢复出厂配置 | 未设置个人覆盖的用户，以及公共未登录页面 |

“我的外观”选择后立即生效并自动保存，显示保存中、已保存或保存失败状态。平台默认区编辑只改变区内预览，点击“保存平台默认”才提交，避免管理员正在编辑时整个应用频繁换色。

普通用户无平台默认权限时，平台默认区不展示。系统配置页面仍遵循原有访问权限；没有系统配置入口的用户通过顶部入口管理本人偏好，不为选择主题额外授予系统管理权限。

新增独立外观查看权限时，必须同步系统配置父路由可见条件，避免“有子页权限但父路由无法进入”。只读平台管理员可预览默认方案但不能提交。

### 4.2 顶部快捷入口

将现有亮暗按钮升级为外观面板：模式分段选项、主题卡片、跟随平台开关及当前保存状态。已具备系统配置访问权时，可提供“更多设置”跳转外观主题页签。

顶部和页签不各维护一套主题状态。主题卡片同时展示配套亮暗缩略图及中文名称；选中态除颜色外还有标记，键盘可操作。长名称与窄窗口下允许合理换行或滚动。

若采用侧滑承载完整设置，必须遵循 [侧滑窗口规范](../drawer-layout-standard.md)：固定 header、标题左侧、操作按钮右侧、仅内容区滚动，并确保不被主窗口 header 覆盖。

## 5. 配置模型、继承与保存

### 5.1 推荐配置结构

```ts
type AppearanceMode = "light" | "dark" | "system";

type AppearancePreference =
  | { schemaVersion: 1; source: "platform" }
  | { schemaVersion: 1; source: "personal";
      themeId: "classic-gold" | "business-blue" | "jade-green";
      mode: AppearanceMode };

interface PlatformAppearance {
  schemaVersion: 1;
  themeId: string;
  mode: AppearanceMode;
  revision: number;
}
```

首期个人设置成组覆盖配色与模式，不引入两个字段分别继承的复杂交互。点击“跟随平台默认”清除个人覆盖；“恢复平台出厂配置”只属于平台管理区，并有清晰作用范围提示。

### 5.2 解析规则

1. 已登录账号有有效个人覆盖：使用个人配置。
2. 无个人覆盖或选择跟随平台：使用平台默认。
3. 平台读取失败：先用有效缓存，首次无缓存使用内置经典金＋system。
4. 最终 mode=system 时才读取系统明暗；系统变更仅影响 system 用户。
5. 无效、已移除 themeId 回退经典金，保留有效 mode，不导致白屏。

账号配置属于全局用户，不按工作区重复保存；切换平台／机构／企业工作区保持个人偏好。未登录页面采用平台默认及匿名本地选择，不读取其他用户私有偏好。

### 5.3 缓存、迁移与竞态

- 旧 `ky.admin.colorScheme.v1` 只在新配置不存在时迁移一次，保留旧显式模式，主题使用经典金。
- 本地缓存区分匿名与账号，账号标识从当前已验证会话取得；登出切回匿名／平台外观，不能沿用上个账号私有缓存。
- 首次登录：服务器已保存偏好优先。旧设备级亮暗值仅作为升级兼容的本机临时覆盖，不自动上传为某个账号的偏好；用户首次明确选择或点击采用当前设置后，才保存为个人设置。选择跟随平台时清除此临时覆盖，避免旧值永久压过平台默认。
- 会话过期、切换账号时取消待提交任务；响应必须核对账号及请求序号，旧响应不能覆盖新选择。
- 连续切换采用短防抖并只保存最终状态；失败保留本地显示，明确“仅在本机生效，尚未同步”，提供重试，不能假提示成功。
- 同设备标签页通过现有 storage／事件机制同步；本地版本与服务端 revision 分开，不依赖客户端时钟判断新旧。
- 跨设备不要求实时推送；登录、重新进入设置或窗口恢复焦点时刷新。保存冲突保留草稿并提示重新读取，不覆盖他人更新。

## 6. 主题架构与颜色规范

推荐在 `packages/ky-admin-core/src/` 新增独立主题目录，具体文件名在实施时确定：

```text
theme/
  types.ts          主题类型与语义 token
  presets.ts        受控配色及亮暗定义
  resolve.ts        校验、继承、兼容回退
  css-variables.ts  CSS 变量映射
  antd-theme.ts     Ant Design token 映射
  provider.tsx     主题上下文与状态消费接口
```

Host 负责会话及持久化适配，公共包不直接依赖具体业务服务。平台设置插件调用公共主题消费接口，不反向导入 Host 内部实现。

语义 token 至少覆盖：primary、primaryHover、primaryActive、onPrimary、layoutBg、navBg、headerBg、surface、surfaceElevated、surfaceMuted、text、textSecondary、textDisabled、border、divider、selectedBg、selectedText、focusRing、shadow、scrollbar，以及 success/warning/error/info 及对应前景背景。

CSS 根节点使用独立属性表达配色与最终明暗，例如 `data-admin-palette="business-blue"` 与 `data-admin-theme="dark"`，`color-scheme` 只写 light/dark。保留现有变量名作为兼容层，逐步收敛，不让插件自行拼接主题值。

Ant Design 算法仍按最终亮暗选择，其 token 与 CSS 均来自统一解析结果。现有仅根据操作系统的 CSS 媒体特例改为明确的最终模式，避免显式亮色和系统暗色互相覆盖。

布局、圆角、字体和间距不属于本轮配色配置。保留 Logo 居中及最小 16px 两侧间距、侧栏尺寸和已有状态保持行为。

## 8. 服务端、权限与接口建议

以下是设计目标，端点名和数据库迁移编号尚未落地，实施前按现有 API 契约确认。

| 能力 | 归属建议 | 约束 |
| --- | --- | --- |
| 获取本人外观、保存／清除个人覆盖 | Auth 服务本人偏好能力 | 登录本人可用，服务端取 actor ID，不接收任意目标用户 ID |
| 平台默认查询与更新 | Org 服务系统配置能力 | 复用作用域存储，受控键 appearance，独立校验、revision 与审计 |
| 公共页面默认主题读取 | 公共安全配置 | 仅返回受控主题与模式，不公开其他系统配置 |

推荐平台权限：`platform.appearance.view`、`platform.appearance.update`；需注册权限目录、角色授权树及系统配置路由条件，不能只在前端隐藏按钮。默认权限绑定遵循现有角色治理，不自动扩大普通角色授权。

平台默认写入与审计在同一事务完成，记录操作者、前后值及 revision。个人偏好为高频低风险设置，按现有日志策略记录，不逐次生成管理审计通知。

本次检索 Auth 路由与实现未发现可直接复用的个人偏好接口，实施基线按新增本人外观存储与接口估算；实现前再次确认是否有新增的公共偏好设施。存储以用户 ID 唯一约束，使用增量 migration，不能向组织品牌表写入个人选择。平台和个人的更新均需拒绝非法 themeId、mode、schemaVersion，并保证只更新外观字段。

- 本轮仅后台及桌面外观设置变化，不发布任意主题脚本，不变更菜单和业务权限行为。

## 13. 二次复评结论与修订约束

复评日期：2026-10-29。结论：总体方向合理，可以按分批方案推进；以下约束为本轮修订后的实施基线，优先于前文的概括描述。尚未执行代码实现、数据库变更、提交或部署。

### 13.1 合理性评估

| 决策 | 复评结论 | 原因与边界 |
| --- | --- | --- |
| 明暗与配色分离 | 保留 | 避免每增加一种颜色复制整套主题逻辑 |
| 三套内置主题 | 保留 | 六个视觉组合可控，先完成覆盖而非追求数量 |
| 系统配置新增页签 | 保留 | 符合明确需求；平台默认与个人设置分区显示 |
| 平台默认＋本人偏好 | 保留 | 默认运营与个人体验有不同归属，必须分开保存 |
| 本轮跨设备保存 | 保留，但明确新增成本 | 当前没有已核实可复用接口，需服务端存储、身份隔离和并发协议 |
| 公共包统一 token | 保留 | CSS、Ant Design、预览同源；原生窗口通过桥接消费受控结果 |
| 任意在线调色器、机构级策略 | 延后 | 非当前必要目标，会扩大校验与继承复杂度 |
| 全部页面同一轮适配 | 保留完整交付门槛 | 分批开发，完成全面验收后再开放；不以首页正常代表完成 |

### 13.2 平台设置权限必须封闭所有写入路径

源码证据：Org 的 `settings_handlers.go` 及 `store/settings_store.go` 当前接收 settings 映射，通用平台更新按 `platform.settings.update` 授权，存储层不具备 appearance 专属权限或 revision 判断；审计在写入返回后另外调用。

因此，不能直接向通用接口增加 appearance 键，再声称已具备独立外观权限和乐观锁。实施采用：

1. 外观配置使用专用读写处理函数与结构化输入，按 `platform.appearance.view/update` 校验。
2. 继续复用系统设置表时，专用存储方法负责原子 revision 比较、更新与审计事务；不得先读后无条件覆盖。
3. 原有平台通用更新、工作区通用更新及其他导入／恢复入口必须拒绝 appearance 保留键；通用读取不用于公开默认查询，也不能绕过外观查看策略。
4. 不修改其他设置键的既有语义，不把安全、存储等设置随外观响应一起返回。
5. 权限注册需覆盖服务端目录、角色授权树、插件菜单贡献、`routes.tsx` 父路由条件、页签过滤；`permissions.ts` 当前为空，不能仅在此文件添加字符串即视为完整注册。

### 13.3 偏好生命周期与同步边界

- 不强制用户之间实时同步。个人偏好和平台默认均在登录、重新聚焦、进入外观设置时刷新；同标签即时生效，同设备标签页广播有效变更。文档中的“平台默认更新”不表示已有全站推送。
- 本人保存同样携带服务端 revision。每个账号保存请求串行化，合并尚未发出的连续选择，防止旧请求最后落库。跨标签／设备冲突重新读取并提示，不能只在前端忽略旧响应。
- 保存失败的本地待同步配置单独标记 dirty，后台刷新不得静默覆盖它；退出账号时停止自动重试，不能将待同步内容写入后续账号。
- 账号切换时立即切换缓存命名空间，再请求本人偏好；服务端加载完成前可显示该账号已知缓存，无该账号缓存则用平台默认，不借用上一账号显示值。
- 浏览器禁用或配额不足导致 localStorage 失败时，退化为内存状态并显示无法本地保存，不阻断应用启动。
- 默认解析器分别输出 preferenceSource、configuredMode、resolvedMode 与 themeId，界面可显示“跟随平台／个人设置／本机临时设置”，不能将缓存层误作为业务继承层。

### 13.4 首屏与运行时实现限制

- 首屏脚本只消费已校验的小型本地快照，不解析会话令牌、不发阻塞网络请求。与运行时共用生成的主题清单，避免复制一套颜色映射。
- 首次无缓存且平台默认需要网络读取时，允许使用内置主题启动后进行一次校正；验收应写为“有缓存时减少闪烁”，不能承诺首次访问、跨设备和慢网络下绝对零切换。
- 核验实际 CSP 对初始化脚本的约束，优先构建生成的同源外置脚本；不得为首屏换色放宽脚本策略。
- 主题 Provider 放在稳定应用根部，不给路由／页面／Provider 添加随主题改变的 key。Ant Design 弹层、静态消息调用、Portal 和独立 React 根要单独验证上下文，不能默认继承成功。
- 品牌预览只用局部变量作用域；平台默认草稿的预览不调用全局主题 setter。复杂预览中的 Ant Design 组件需局部 ConfigProvider。
- 原生窗口在首次启动时可能先显示上次已知主题背景，渲染进程准备好后同步最终值；桥接不得将任意 CSS 或任意窗口控制能力暴露给网页。

### 13.5 准入、发布与回滚补充

- P0 输出实际插件清单、固定色清单、弹层与原生窗口清单；实施估算以该清单为准，本文没有给出未经测量的工期。
- P2 需锁定请求／响应、清除个人覆盖语义、revision 冲突码、公共缓存更新策略及迁移编号，再实施数据变更。
- 平台默认响应携带 revision／ETag 或等价版本标识，配置读取缓存须可失效；上线验收包括代理／浏览器缓存，不能仅测服务直连。
- 主题配置与后端可在兼容状态下提前交付，新的用户入口在 P1～P4 验收通过后开放。应急开关必须位于主题配置之外并可独立操作，具体载体在实施锁定时确认。
- 回滚旧前端前需做明确的旧格式投影／兼容桥接验证；不能假定旧版自动理解新主题 ID。兼容桥仅投影最终 light/dark，跟随平台不反写为永久个人覆盖。
- 数字可读性、聚焦态与语义状态可辨识需要逐组合验收；上线前为正文、次要文字、按钮、禁用态、错误提示等建立可测的对比度目标，而不是只凭主题缩略图判断。

### 13.6 实施前需锁定但不改变目标的事项

1. 三套配色的具体色值与亮暗视觉样张。
2. 本人偏好和平台默认的最终 API 名称、数据库 migration 编号与并发协议。
3. 平台默认外观权限赋予哪些现有管理角色，遵循现有角色 seed／迁移规则，不自动给所有管理员全权。
4. 应急停用新主题的独立开关及其发布方式。

这些属于实施设计与视觉验收项，不影响新增“外观主题”页签、多配色双模式及状态保留的需求方向。
