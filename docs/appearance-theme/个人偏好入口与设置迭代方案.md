# 个人偏好入口与设置迭代方案

日期：2026-10-29。状态：二次复评修订版；总体方向已获认可，尚未实施本方案的入口调整。

关联：[多配色外观主题方案](需求与迭代方案.md)、[已有主题实施与验证记录](实施与验证记录.md)、[侧滑窗口规范](../drawer-layout-standard.md)。

## 1. 目标与范围

将本人外观选择收拢到右上角用户下拉的“个人偏好”，形成统一的个人设置入口。首期只承载已经实现的配色主题能力，不在本轮提前上线尚未具备消费者的偏好开关。

区分三类职责：

- 个人偏好：只影响本人账号的显示与使用习惯。
- 系统配置：维护平台默认值，影响没有个人覆盖的用户及公共页面。
- 账号安全与会话操作：修改登录密码、退出登录继续独立保留。

本轮包含用户下拉菜单调整、个人偏好侧滑窗口、外观控件复用、旧入口清理、平台页职责收敛、状态和权限回归。不改菜单业务数据，不扩展新的导航／列表偏好，不部署或修改线上配置。

## 2. 当前源码基线

| 位置 | 当前能力 | 本轮处理 |
| --- | --- | --- |
| Host `app.tsx` 用户 Dropdown | 用户信息、条件展示的切换工作区、修改登录密码、退出登录 | 加入个人偏好，保留条件菜单及原操作 |
| `appearance-menu.tsx` | 顶部独立外观按钮及 Popover | 按本方案建议移除独立入口，复用内容能力，不再维护第二份个人表单 |
| `appearance-provider.tsx` | 本人偏好、平台默认、即时应用、自动保存、缓存和同步 | 保持为唯一状态来源，不在 Drawer 内重建 Provider |
| Core `theme/controls.tsx` | 配色与明暗控件 | 在个人侧滑及平台默认页复用 |
| 系统配置 `appearance-page.tsx` | 我的外观、平台默认两个区块 | 移出个人区块，仅保留平台默认管理 |
| `settings-hub-page.tsx`、插件 routes/index | 系统配置外观页签与入口权限 | 外观页签恢复为专用平台查看权限过滤 |

## 3. 用户下拉设计

推荐顺序：

```text
用户名称
角色／当前身份
────────────
切换工作区      （沿用现有显示条件）
个人偏好
修改登录密码
────────────
退出登录
```

要求：

1. 菜单项使用“个人偏好”，不叫“系统设置”，避免和平台配置混淆。
2. 配套设置类图标，继承当前主题、字号、间距与悬停效果。
3. 点击先关闭用户 Dropdown，再打开个人偏好 Drawer，避免两个浮层重叠。
4. 保留用户摘要、切换工作区条件、密码修改和退出登录的既有处理链路。
5. 用户摘要继续只读；首期不增加头像上传、昵称编辑等账号资料能力。
6. 顶部原独立主题按钮建议删除，减少重复入口；其余顶部按钮顺序和功能保持原职责。

本轮以移除顶部独立主题按钮作为评审基线；实际视觉和交互仍须实施后验收。删除入口不删除主题 Provider、首屏初始化、同步和客户端桥接。

## 4. 个人偏好侧滑窗口

### 4.1 承载与布局

- 标题为“个人偏好”，从右侧滑出，建议复用 `drawerWidths.standardForm`，不写新的固定窗口尺寸。
- 采用项目原生 Drawer 的 title、关闭入口和 body；不在新窗口或新路由中打开。
- Header 固定，标题靠左；保留组件自带关闭入口。首期自动保存，不人为增加保存、提交或取消按钮，也不重复生成关闭按钮。
- 抽屉根容器、遮罩与内容一起避让主 Header 和客户端状态栏；仅正文滚动，不用单纯增大 z-index 解决遮挡。
- 窄屏遵循项目宽度表达式，允许字段和主题卡片换行，不能横向溢出。
- 首期只有“外观”一个分组，直接展示，不增加只有一个选项的内层 Tabs 或空白侧栏。
- 后续确有第二类偏好时再增加分组导航；不展示“导航、列表、提醒”等尚不可用的空栏目。

### 4.2 首期字段

| 项目 | 类型与内容 | 行为 |
| --- | --- | --- |
| 使用平台默认 | 开关或明确的继承选择项 | 开启时清除本人覆盖；关闭后以当前有效值初始化个人选择 |
| 外观模式 | 亮色／暗色／跟随系统 | 个人模式下可修改；system 只决定明暗，不改变配色 |
| 配色主题 | 经典金／商务蓝／翡翠绿 | 展示亮暗缩略图、中文名称及明确选中标记 |
| 当前来源 | 说明文字 | 区分跟随平台、个人设置、本机兼容或尚未同步 |
| 同步状态 | 状态与必要的局部操作 | 保存中、已保存、同步失败；失败时可重试或重新读取 |

使用平台默认时，展示最终生效的主题与模式，并将个人选择控件设为只读；用户先关闭继承再修改，避免“开关仍显示继承但实际已自定义”的矛盾。

继承选择属于设置字段，可以位于正文。首期不增加正文末尾或底部的全局“保存／恢复”操作栏。未来若加入窗口级提交或重置操作，必须放在 Header 右侧。

### 4.3 保存与关闭语义

- 继续即选即生效、自动保存；抽屉没有“取消本次修改”的语义，关闭不会撤销已经生效的个人设置。
- 保存任务及失败草稿由应用级 Provider 管理，关闭抽屉不取消必要同步、不清空待同步选择；重新打开继续显示状态。
- 保存失败说明“仅在本机生效，尚未同步”，允许关闭；重试不能覆盖服务器较新版本。
- “重新读取”会替换本机尚未同步的选择，操作前明确提示作用；只有用户确定后才丢弃本地草稿。
- 快速切换继续使用已有防抖、串行提交与 revision 检查，不因抽屉开关重新发起一组写请求。
- Escape、遮罩和 Header 关闭行为沿用项目 Drawer 约定，不把关闭按钮设计成保存按钮。

## 5. 平台设置职责调整

系统配置保留“外观主题”页签，但只展示平台默认管理：默认配色、默认模式、亮暗预览、保存及恢复出厂草稿。此处不再展示“我的外观”。

| 场景 | 推荐行为 |
| --- | --- |
| 已登录且已进入工作区的用户 | 用户下拉可打开本人偏好，不额外要求平台配置权限 |
| 有平台外观查看权限 | 可以进入系统配置的外观页签并预览平台默认 |
| 有查看但无修改权限 | 平台表单只读，不能保存或恢复出厂草稿 |
| 无平台外观查看权限 | 不显示平台外观页签；本人设置仍可从用户下拉使用 |
| 已有 appearance 深链接 | 保留原 URL；有权继续查看平台默认，无权按既有页签回退规则处理 |
| 只有新外观查看权限的管理员 | 父路由、插件菜单贡献和页签过滤均允许进入，不能有子权限却被父路由拦截 |

保留 `platform.appearance.view/update` 的接口授权；个人开关仍调用本人 API，不能借平台接口保存。

## 6. 生命周期与状态保留

1. Drawer 建议挂在稳定的登录后 Host 布局层，不作为业务插件的页面内容，不随主题、导航类别或正文滚动重挂载。
2. 切换配色只更新已有上下文和变量，不给 Drawer、业务路由或 WebView 增加随 themeId 改变的 key。
3. 切换工作台／管理中心不重置已保存偏好；同一账号时 Drawer 可保持打开。
4. 切换工作区时关闭 Drawer，个人偏好本身保持不变；重新打开读取同一全局账号偏好，不按工作区重复保存。
5. 登出、会话失效或更换账号时关闭 Drawer，终止旧会话的未发出写请求，不能让旧响应覆盖新账号状态。
6. 失败草稿按账号隔离，恢复、同步与显式丢弃沿用主题方案规则。
7. 私有缓存／localStorage 不可用时提示退化，不阻断打开个人设置或整个应用。
8. Drawer 中的开关、主题卡片和同步状态与当前实际外观始终一致，不另设临时主题 Provider。

## 7. 客户端与 WebView 的浮层要求

本轮入口在顶部用户菜单中，必须分别验证 Web 与 Electron：

- 用户 Dropdown、个人偏好 Drawer、内部下拉及提示均不能被原生 WebView 遮挡。
- 不能通过隐藏、销毁、重新创建、重新导航 WebView 来显示偏好窗口。
- 不将外部网页换色作为个人偏好的作用范围，仅应用外壳、工具栏、占位区域和原生背景同步。
- 优先复用项目现有浮层承载机制。实施前核对当前 WebView 类型及层级；若普通 DOM Drawer 无法覆盖原生视图，必须先解决实际承载关系，不能宣称加大 CSS z-index 已完成。
- 打开、切换主题、关闭偏好后，验证业务网页的登录态、滚动、浏览历史和输入内容保留。

## 9. 数据与 API 演进边界

首期继续复用：

- GET／PUT `/api/v1/auth/me/appearance`：本人选择和继承。
- GET `/api/v1/public/appearance`：安全的默认值读取。
- GET／PUT `/api/v1/platform/appearance`：平台管理。

不新增 `ky_user_preferences` 总表，不复制用户身份或另设一个保存接口。现有 schemaVersion、revision、账号缓存、跨标签同步和异常处理继续使用。

后续增加导航／列表等设置前，再设计按分组保存的个人偏好合同，避免保存表格密度时覆盖同时修改的外观设置。即使增加通用偏好服务，首期 appearance 接口也须有兼容迁移路径，不直接复用平台系统参数表存个人数据。

## 14. 二次复评结论与实施约束

复评日期：2026-10-29。结论：统一个人入口、沿用自动保存、平台配置独立管理的方向合理，首期范围可控；以下补充为修订后的实施基线。此次只修订方案，不执行入口改造、数据库操作、提交或部署。

### 14.1 入口可达性与权限收敛

源码中的用户下拉位于 `WorkspaceLayout`，并非每个已登录页面都有该 Header。因此，“本人偏好不需平台权限”是授权规则，不等于无工作区、登录页或工作区选择页已经存在入口。首期覆盖当前工作台与管理中心；无有效工作区的账号仍保留已有外观消费能力，本轮不扩展登录前／工作区选择页导航。

系统配置移除“我的外观”后，需要完整处理两类情况：

1. 账号仍有其他系统配置查看权限：外观页签不可访问时回退到第一个有权页签，并同步规范化 URL，使用 replace，避免浏览器后退反复跳回无权 tab。
2. 账号没有任何系统配置查看权限：父路由继续拒绝访问，沿用已有无权限页面；个人偏好仍通过用户下拉可达。不能为了旧的个人 appearance 链接扩大系统配置授权。

当前 `settings-hub-page.tsx` 只对有效显示项计算 activeKey，不能默认它已经将无效 URL 修正。本轮需要补齐 URL 与显示状态一致的处理；补齐仅限已有页签导航合同，不改其他页签权限。

只有 update、没有 view 的账号不自动获得查看或入口权限。若角色配置需要两者，按既有授权方式配置，不能在前端补权。平台公共默认信息本来用于所有用户的外观消费，管理权限控制的是管理入口与写入，并非将主题 ID 作为机密信息。

### 14.2 继承开关的精确语义

- 开启“使用平台默认”：通过已有本人接口写入 source=platform、themeId/mode 为空，带上当前本人 revision；清除覆盖不删除记录或重置版本。
- 关闭继承：复制当前有效的 themeId 与 configured mode 创建个人覆盖。若平台配置为 system，复制 system，不能复制当前解析出的 light/dark。
- 关闭继承后即使外观暂时没变，也应保存个人来源；平台日后变更不再影响该账号。
- 首期不承诺恢复开启继承前的某套历史个人配色。重新关闭继承以当时平台有效设置为起点；若未来需要“记住上次自定义”，另设计跨设备数据语义，不能仅在一个标签页私存后暗示全端可恢复。
- 系统跟随、平台继承是两个不同概念。界面说明应分别写清，避免“跟随系统”被理解为跟随平台。
- 初始化尚未完成时显示加载状态，不能让一个暂时的默认值看起来已经是服务器确认的本人选择。断网且无法核实服务器配置时，允许本机暂存须明确标识，不能提示账号已保存。

### 14.3 保存与显式重新读取互斥

Provider 目前有串行保存和 revision 检查，但当前 `reloadPersonal` 并不等待全部在途 PUT。仅在 Drawer 上增加确认框还不能证明没有竞态。

本轮应将“重新读取并放弃本机选择”做成应用级受控动作：

1. 确认提示使用现有 Ant Design App 上下文，避免静态弹窗脱离主题；无 dirty 时正常读取，不重复确认。
2. 提交中禁用重新读取；若有已排队但尚未发送的防抖任务，用户确认后取消排队，再读取服务器。
3. 在途写入不能靠 abort 宣称已撤销。必须先确定其结果或结束状态，再进行替换；响应不明时保持 dirty 并允许重试核对，不自动清除草稿。
4. 读取开始后用操作序号或等价机制隔离旧响应。读取期间若用户又作出新选择，旧读取不能覆盖新选择；可以短暂禁用选择控件简化交互，但不能阻塞关闭窗口。
5. 读取成功并确认响应归属当前账号后，才清除本机 dirty／冲突状态；失败继续保留原选择。

上述是与本轮新增“明确丢弃”操作直接相关的小范围正确性修复，仍复用原接口与存储，不重写整套同步架构。

### 14.4 窗口状态、来源与互斥

- Drawer 本身不拥有偏好草稿或保存队列，沿用根级 Provider。打开／关闭只改变可见性，不能触发保存。
- 用户下拉建议以受控 open 状态关闭，处理相同事件中的菜单选择和抽屉打开；不依赖动画延时或多次 setTimeout。
- 个人偏好、修改密码、切换工作区等 Header 管理浮层避免同时打开。打开一个时关闭其他相关 Header 浮层；不得关闭正文中的业务表单来达成互斥。
- 工作区切换的关闭条件至少包含 workspace type/id，避免仅比较 id 造成跨类型漏关；更换用户、登出或进入锁屏时也关闭，解锁后不自动重开。
- 自动保存成功、失败、冲突、初始化，以及本人／平台／旧版本机来源应有结构化上下文状态；不能在 UI 中匹配中文 status 字符串来决定开关行为。
- 当前 Provider 的 legacy 标记是内部 ref，仅凭 preference.source 无法准确区分本机旧版兼容与已同步个人偏好。本轮允许增加只读的上下文元数据，不新增后端字段或数据库表。
- 应急停用新主题时，个人偏好入口仍可打开并显示停用说明，不提供无效主题控件；不要将整个个人偏好模块永久绑定到主题启用开关。

### 14.5 浮层与 WebView 证据边界

本次检索 `apps/aicrm-desktop/src` 和 `apps/ky-admin-host/src`，未发现直接创建 `WebContentsView`、`BrowserView` 或启用嵌入式 webview 标签的实现；当前账号登录／浏览窗口存在独立 BrowserWindow，插件执行窗口明确关闭 webviewTag。这不足以证明历史截图中的客户端、其他仓库或外部插件没有原生嵌入式视图。

因此，本轮处理分层：

- 当前 Host 页面：先按原生 DOM Drawer 及既有宿主可用边界实现并验证。
- 如果验收环境确有原生嵌入式视图：先确认客户端构建来源、视图类型和已有覆盖机制，再验证浮层。不能将旧环境的实现当成当前源码既有能力。
- 只有实际复现层级冲突时才实施必要的承载适配；不预先扩展成新的原生浮层或多窗口架构，不以未接入的历史 WebView 场景阻断当前普通页面实现。
- 仍保留用户明确约束：不允许隐藏、销毁或重建 WebView 来显示设置；存在原生视图时，完成该场景的真实验收才能声称已解决覆盖。

### 14.6 范围与验证修订

本轮“不新增数据库迁移”指不在已实现的迁移 106 之上新增入口专用迁移，并不表示可以把尚未部署的原主题服务端／迁移省略。发布入口改造时仍需按原主题实施记录完成相应部署依赖。

增加以下必测项：

| 补充场景 | 验收结果 |
| --- | --- |
| 平台 mode=system 时关闭继承 | 个人保存仍为 system，系统变化仍可改变明暗 |
| 开关继承但当前视觉相同 | 来源正确保存；平台日后更新只影响继承者 |
| 在途保存时请求重新读取 | 不提前清 dirty，不发生旧 PUT 最后落库覆盖读取结果 |
| 已排队保存后确认丢弃 | 排队任务撤销；服务器值读取成功后再更新本机来源 |
| 初始化／断网／应急停用 | 状态明确，无虚假成功或无效控件 |
| 锁屏／换账号／跨类型工作区 | 抽屉关闭，旧请求不串入新上下文 |
| 仅个人偏好、无任何系统配置权限 | 用户菜单可用；旧系统深链接走现有无权限路径 |
| 无权 appearance 但有其他页签 | 实际页签和 URL 一致，后退无回退循环 |

评估后的实施顺序仍为 P0～P4；P0 先锁定当前承载和同步操作边界，P1 把来源、继承与重读互斥做正确，P2／P3 再统一入口和平台页职责。各阶段验证具体变更，不为入口调整扩展导航、语言、时区等候选功能。
