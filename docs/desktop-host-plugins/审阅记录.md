## 1. 审阅方法与规范映射

所读 `aicrm-solution/SKILL.md` 提供四项任务闸口和验证要求，没有规定必须几轮或必须另一 AI 签字。“逐条问题登记 → 修订 → 交叉复审 → 锁定”是依据用户要求组织的审阅流程，不伪称 Skill 原文规定了轮数。

| 闸口 | 本轮回答 | 对照位置 |
| --- | --- | --- |
| module-boundaries | Electron 新独立宿主负责本地插件安全与生命周期；Web 只负责槽渲染，业务插件/服务不改职责 | 方案 §2–5；reference 的 Desktop/Plugin/Host 边界 |
| permission-data-scope | 本地能力交集授权，零 token/工作区/业务请求；不新增角色/seed，不把签名当 RBAC | 方案 §4、7；仓库权限矩阵 §11、14 |
| api-contracts | 无新增 HTTP 业务 API，静态签名分发独立；固定 IPC DTO、错误、CAS、版本和幂等边界 | 方案 §6–9；仓库 API §2 |
| event-communication | Query/Command/Native Event 分离；集中 channel、sender 校验、快照序号、订阅清理、非 Desktop 降级 | 方案 §4–6、9；通信规范 §12、15、17 |
| 治理与兼容 | monorepo 内独立包发布，首次宿主升级；旧宿主/旧 Web/离线矩阵；回滚不越数据边界 | 方案 §3、5、10–11；仓库治理 §9–10 |

通信规范 §15 逐项结论：版本读取是 Query；投影提交是本地 Command；生命周期与变更是 Native Event；纯展示点击不是业务事件。Main 必经的原因是调用授权、安装目录和进程生命周期属于原生边界；显示组件不经 Main 操纵 DOM。新增 channel 和类型有明确归属；消息无敏感数据；订阅返回 unsubscribe 且 effect cleanup；快照与增量并存；浏览器/旧版本有降级；生产与开发来源分开；不转移登录/工作区/权限所有权。

## 2. 分级与处置规则

- P0：可跨越安全边界、执行未授权代码、泄露凭据或损坏业务数据。未解决不得锁定。
- P1：核心更新/恢复/兼容闭环不确定，或验收不可重复。未形成具体合同不得锁定；合同明确但未实现的测试列为交付硬门禁。
- P2：明确边界内的体验、运营或后续治理优化，可注明范围与条件后进入路线图。

“设计已处置”只表示方案给出了可以测试的规则，不表示安全缺陷已修复或测试已通过。
