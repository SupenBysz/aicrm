## 4. F01：原生层级与锁屏

### 4.1 推荐结构

推荐保留一个业务 WebContentsView，并新增由主进程管理、仅加载本地可信 UI 的原生宿主浮层承载面。采用同一父窗口内、业务视图上方的独立 WebContentsView 作为首选验证方案，避免把整个主 UI 重新挂载到另一窗口。

```text
父窗口
├─ 现有宿主 WebContents：导航、业务路由、根级状态和普通 Web 页面
├─ 业务 WebContentsView：第三方页面、原会话、滚动与浏览历史
└─ 可信浮层 WebContentsView：侧滑/确认框，锁屏时切换为不透明安全界面
```

主进程统一管理子视图顺序。创建、重新激活业务视图时，都必须再次确保可信浮层位于最上层；不能只在首次打开浮层时排序。

Electron 官方 View API 支持原生子视图顺序调整；已经存在的子视图再次加入会成为最上层。[官方 View 文档](https://www.electronjs.org/docs/latest/api/view#viewaddchildviewview-index)。这提供实现基础，但不证明透明合成、焦点和多显示器行为已在本项目通过。

### 4.2 先做最小技术验证，再扩展 UI

实施第一关必须在仓库锁定的 Electron 43 及 macOS 实测：

- 透明浮层能在不隐藏业务视图的情况下绘制侧滑及背景遮罩，下方仍为实时页面。
- 普通浮层范围、输入命中、透明背景没有黑底、闪烁或网页穿透操作。
- 父窗口移动、缩放、最大化、全屏、跨 DPI 后，原生层级与边界仍正确。
- 浮层内容关闭后移除/停用的是浮层自身，业务实例、URL、历史、滚动和会话不变。

若同窗口透明合成或输入行为不满足上述条件，停止扩展该承载面，记录复现，再评估可信父子 BrowserWindow 方案。不能静默降级为隐藏业务视图。父子窗口也必须保持原视觉与定位，并验证平台差异；例如 Electron 官方说明 macOS 模态子窗口可能以 sheet 展示，因此不能直接用 modal=true 替换原侧滑。[BrowserWindow 文档](https://www.electronjs.org/docs/latest/api/browser-window)。

此技术验证是待做工作，不是已经完成的选型验收。平台不支持时明确阻断该平台的新 WebView 功能，不宣称跨平台已解决。

### 4.3 普通浮层合同

| 场景 | 预期 |
| --- | --- |
| 个人偏好、密码、工作区切换等宿主侧滑 | 同原 Header/正文/按钮结构，在可信原生浮层中展示；业务 WebView 保持实例与加载状态 |
| 侧滑内确认框、错误和下拉 | 在同一承载面内部继续按 DOM 层级显示，不再落到业务网页下面 |
| 其他页面内 Drawer/Modal | 新原生菜单页面没有业务 DOM 表单；对可能在该页面同时出现的宿主入口建立清单，不能遗漏已有 Header/状态栏入口 |
| 无原生业务视图时、浏览器运行时 | 使用原有 DOM 路径和共享组件，不启动无必要的原生承载面 |
| 系统原生文件选择等窗口 | 保持父窗口归属，验证焦点与恢复顺序，不以高层置顶覆盖系统对话框 |

普通侧滑的原生承载矩形应避让实际 Header 和状态栏，不能用透明的全窗输入层无意截断窗口按钮、用户菜单或状态栏的点击。仅在明确的全窗模态/锁屏场景覆盖整个内容区；每类浮层的绘制区域、输入区域和允许继续操作的宿主入口需一起定义。

视图与数据控制分开：复用现有侧滑展示组件、表单校验和主题组件；根级 Provider/控制器仍是唯一写入者。个人偏好浮层消费经过校验的状态投影，发送有类型的选择/重试等动作，不能再创建第二套账号缓存、保存队列或平台默认写入口。

第一批必须覆盖实际可达的个人偏好、密码、工作区切换、网络日志、版本信息和锁屏。公告等会发生路由离开的入口需确认先停用原页面视图；Tooltip/用户下拉等位于业务视口之外的浮层验证边界后可保留 DOM。实现时维护“入口—承载面—焦点—关闭”清单，不能靠临时提高 z-index 收尾。

### 4.4 锁屏是主进程状态，不是 DOM 提示

建议状态：`unlocked → locking → locked → unlocking → unlocked`。主进程持有按 owner/登录身份隔离的锁定状态；renderer 的 localStorage 仅作展示/恢复提示，不能通过 renderer 声称 unlocked 就解除锁定。

操作顺序：

1. 收到经过 sender 校验的锁屏请求，先进入 locking，阻止该 owner 的新开菜单、导航、脚本动作、激活实例和普通浮层请求。
2. 将预先准备的可信浮层置顶，以不透明背景覆盖父内容区，焦点移至锁屏界面；关闭已有普通浮层，但保留根级保存状态。
3. 确认遮罩与输入拦截生效后进入 locked。覆盖父窗口的所有业务原生视图，并处理该 owner 的独立业务窗口，不能只挡住主窗。
4. 解锁通过既有服务端认证链路确认同一账号，主进程核验 owner、身份及锁屏代次。错误密码、超时、陈旧响应、仅修改本机标记均保持 locked。
5. 解锁成功后重新确认当前会话/工作区授权，再恢复原激活视图与焦点；不重新 loadURL 恢复页面。

锁定期间还须拦住已有焦点、快捷键/菜单、延迟导航完成后的自动激活和待处理 IPC。先锁定再收到的 did-finish-load 不能重新把业务视图激活。覆盖策略同时适用于嵌入与独立窗口，主进程命令门禁是必要条件，但不能代替鼠标/键盘的原生遮罩实测。

应用刷新、窗口重新聚焦或 renderer 重载不能自动解锁。锁定状态应与身份生命周期一致；退出账号后释放旧会话上下文。安全承载面异常时禁止退回仅有 DOM 的“伪锁屏”；必要时退出受保护工作区，不能继续开放业务操作。此故障退出不是普通浮层隐藏 WebView 的替代方案。

这只定义应用内的锁屏保护，不将其描述成操作系统级屏幕捕获或管理员防护。

### 4.5 IPC 和状态隔离

- 新增独立 sender role，例如 `host-overlay`；通过主进程创建登记并限制到本地可信固定入口，验证 mainFrame、owner、身份代次、工作区和允许动作。
- 独立、最小 preload；不暴露原 main 全量桥接，不开放任意 URL、源码执行或 IPC 转发。
- 浮层使用 sandbox、contextIsolation、关闭 Node 集成、禁止新窗口/跨源导航和不需要的权限。
- 投影只含本浮层所需显示字段，不发送认证 token、Cookie、运行脚本源码。密码只走已有安全认证通道，不写本地存储或日志。
- 主题投影包含受控 themeId、配置 mode 与实际 dark；消费同一套 token，不保留原生窗口中仅两色硬编码的副本。
- 所有迟到返回均核验会话/owner/operation 代次。父窗口关闭、登出或身份变化时取消订阅并关闭旧浮层。

## 5. F02：配置读取、草稿与保存不串写

### 5.1 唯一目标与状态机

定义目标键：`directoryType + menuKey + workspaceType + workspaceId + configScope`，独立维护 drawerSessionId 与递增 readGeneration。不可只比较 revision，相同 revision 可能属于不同菜单。

抽屉状态为 `closed / loading / ready / saving / conflict / error`；表单草稿必须携带其实际来源目标、来源 revision、是否继承和脏标记。切换目录、菜单、工作区、范围或关闭窗口均使旧读请求失效。

### 5.2 读取流程

1. 打开/切换前处理未保存草稿：有修改时允许保留当前或确认放弃，不能无提示丢失。
2. 在发请求前清空旧目标的值/revision，进入 loading，禁用保存，使用 AbortController 配合代次核验。
3. 响应只在完整目标、drawerSessionId、generation 与身份仍匹配时落表单；取消本身不能代替代次校验。
4. 明确区分不存在当前范围配置、读取失败及无权限。只有确定的 not_found 可进入空配置创建态；超时/403不能当作空配置后保存。
5. common/workspace 各有自己的 revision。继承来的 common 值可以作为新 workspace 覆盖的起始内容，但不能把 common revision 当作 workspace revision。
6. 从已有配置切到不存在的范围时，明确“以继承配置创建覆盖”或空表单策略及提示，禁止残留上一目标的隐性草稿。

### 5.3 保存流程

- 表单提交时冻结不可变目标、已校验值、原 revision 和 mutationId；请求构造及回调均使用此快照，不引用随后变化的 configMenu/directory。
- 保存中禁用重复提交、编辑目标和范围切换；若允许用户关闭窗口，保存仍归属原目标，迟到成功不能关闭/覆盖新窗口。
- 更新继续要求已有 expectedRevision 与请求头匹配；409/428保留草稿并提示重新读取，不自动拿最新 revision 覆盖服务器。
- 新建遵循原接口创建语义；服务端仍执行唯一键与权限检查，不能通过省略 revision 变成无条件更新。
- 只有目标仍匹配才回填保存结果。无论 UI 是否仍打开，成功后可定向失效原目标查询；避免将全局缓存切到错误菜单。
- 结果不明时先读取原目标核对，不自动重复创建或重放覆盖。该规则与已有个人偏好同步保护保持一致。

### 5.4 表单体验和抽屉规范

固定 Header 左侧标题、右侧保存/取消或关闭，正文独立滚动，并避让实际宿主 Header、状态栏；不能假定所有窗口 Header 高度相同。WebView 配置表单保留 URL、平台、协议、资源版本与调度字段，允许先沿用贡献 JSON 编辑，但必须校验格式并给出中文字段错误，不能直接展示 JSON.parse 异常。

本轮不自动扩展到店铺登录空间绑定：贡献模型目前没有承诺该能力，若后续替换达人广场店铺会话，需要单独建立会话来源/店铺权限合同，不能静默改用公共持久化分区。

## 6. F03：视口、区域切换和实例激活

### 6.1 在真实挂载后绑定

将“打开/取得实例”与“绑定 DOM 测量”拆开。使用回调 ref 或依赖真实 element 的 useLayoutEffect；setOpenMode 不代表 DOM 已经提交。

- element 与有效实例同时存在后，绑定 ResizeObserver、IntersectionObserver、祖先可见性 MutationObserver，以及必要的滚动、resize、visibilitychange。
- 首次立即测量；ref 置空、实例/账号/工作区变化时完整清理 observer、事件和 RAF。
- 祖先链改变时重绑，不只监听初次父节点；侧栏开合、区域切换、路由缓存和动态错误横幅都要触发正确布局。
- 去重、合并 RAF 更新，避免读写布局循环；不能用持续高频轮询替代缺失的订阅。

### 6.2 激活权与旧结果

主进程是当前激活实例的唯一裁决者。按 owner 维护 activeInstanceId、activationId；每次切换产生新激活代次，setBounds 携带该代次和递增 boundsSequence。

迟到的旧区域测量可以被忽略，但不能把旧视图重新置为 active。单独一次 setBounds 不能拥有切换激活权限；它只能更新当前实例合法承载区的几何信息。异步 open、loadURL、ready 回调也必须服从当前激活和锁屏状态。

切换到管理中心时停用非活动工作台视图，恢复时复用同一实例；这是区域激活行为，不是普通侧滑的隐藏方案。实例重建仅用于明确关闭、失效、崩溃或安全生命周期结束。

### 6.3 坐标合同

renderer 提供 CSS 像素矩形；主进程按宿主 zoomFactor 转为窗口内容坐标，再限制在合法业务承载区。不要重复乘操作系统 scaleFactor。空矩形、不可见祖先、后台标签和父窗口最小化均有明确的不可激活结果。

原生浮层几何、业务视口、顶部/底部边界共用同一个 owner 布局代次。重点测试窄窗口、100%/125%/150%缩放、Retina、多显示器、最大化及全屏；不得只用固定1180×760坐标通过测试。

## 7. F04：打开响应与实时状态握手

### 7.1 推荐接口增量

以下为待实现合同，不是当前已有字段：

| 消息 | 新增或明确字段 | 用途 |
| --- | --- | --- |
| open请求 | clientRequestId、请求上下文代次 | 区分重试、切换与迟到响应 |
| open响应 | instanceId、openMode、activationId、完整stateSnapshot | 不依赖下一次事件才能知道已加载/失败 |
| stateSnapshot/changed | instanceId、navigationGeneration、stateSequence、状态/标题/URL/错误 | 顺序比较与状态恢复 |
| setBounds | activationId、boundsSequence | 阻止旧测量复活非活动视图 |
| close/deactivate | 对应激活/操作代次 | 旧清理不能关闭刚被新操作复用的实例 |

导航代次、状态序号与激活代次分别表达不同语义，不能用一个不说明范围的 generation 混用。

### 7.2 接收顺序

1. renderer 先订阅，再发起带 clientRequestId 的 open。
2. 主进程返回原子状态快照；新开和缓存复用使用相同返回合同，不固定返回 loading。
3. open 未完成期间的 changed 暂存为每实例最新序号，数量和存活时间有界；账号/工作区变更立即清空。
4. 收到 open响应后确认当前请求仍有效，在快照和暂存事件中选择最新合法状态；之后只接收同实例同上下文的更新。
5. 旧 loading 不得覆盖已 ready/failed 的同一导航；新导航可以显式重新进入 loading。
6. open结果返回时页面已卸载或另一请求接管，按激活代次停用/释放其资源，不能把共享缓存的新激活实例一并关闭。

初次加载、缓存复用、loadURL失败、资源局部失败都必须有最终状态。资源失败应显示告警并保留可用网页；关闭事件与崩溃后提供可操作的重试，不保留僵尸 loading。

初始占位需要中性主题背景和“正在验证权限/初始化页面”说明；授权失败与网页加载失败要区分，不把系统内部错误码直接作为唯一用户提示。

## 8. F05：版本信息保持原效果

保留贡献者独立 preload、sender 校验、父窗口生命周期及实例复用控制器；修正其视觉承载，而不是删掉原生能力或新造整套版本模块。

## 18. 复评结论与修订决策（2026-10-30）

### 18.1 总体判断

沿用贡献代码、统一菜单来源、保留页面状态及采用原生层级解决遮挡的方向合理。但原方案将部分缺失功能当成回归项，低估数据合同变化，并把原生候选结构写得过于确定。按以下决策修正后，方案可进入分批实施；不能据此宣称技术验证、代码修复或部署已完成。

本次重新核对107迁移及MenuDirectory Store：目录主键为(directory_type, menu_key)，只有单一permission_code及workspace_types；配置revision绑定具体行，现有接口仅读取/保存。下述多工作区映射和恢复继承并发设计属于补充设计，尚未实现。

### 18.2 目录、路由与权限的职责

1. **可信路由注册表**决定内部模块是否存在及可跳转的routeKey。服务端只接受受信任构建清单中的内部路由；管理员可以修改展示元数据，不能通过任意routePath注册可执行模块。缺失模块列入诊断，不能生成看似正常的死入口。
2. **有效菜单目录**决定名称、图标、父级、顺序和启停；目录不承担实际业务授权。分组是结构节点，不强行生成权限码。真实导航、管理树和授权树共用结构投影，各自应用不同可见/可编辑规则。
3. **权限绑定**区分菜单进入权限和页面/操作权限归属。先盘点平台/机构/企业差异，再采用工作区感知的显式绑定；一个菜单可关联多个权限，同一权限可归属多个菜单。不能将单一permission_code作为全部关系，也不能按名称/资源前缀自动授予权限。具体表名和迁移编号在A批固定，不为尚未核实的差异机械增加表。
4. 授权编辑数据来自服务端可分配权限集合，不能以“当前用户导航里看得到的菜单”过滤可编辑权限。树中重复展示的权限共用稳定permissionId和同一选择集合，计数去重；四类筛选仅改变视图，不能改变选择集。服务器再次检查可授予范围及受保护角色规则，客户端保留隐藏ID不等于获得写入授权。

### 18.3 初始化与切换条件

- 区分内置基线、插件清单与管理员覆盖；版本升级只补齐新增项/更新未覆盖字段，不用全量upsert覆盖管理员的名称、图标、排序和停用设置。基线版本及字段覆盖来源必须可解释。
- 切换新导航前按目录/工作区检查初始化版本、有效路由、权限映射和无环结构。检查未完成时保持整套旧路径并显示管理诊断，禁止一半静态一半动态拼接。
- 一旦切换到新权威目录，服务端返回的合法空目录、停用结果和无授权结果必须生效；请求失败显示错误/重试，不能回退静态菜单而复活已停用或无权入口。初始化未就绪与合法空结果使用显式状态区分。
- 历史清理先生成路由/资源/角色引用及影响清单。用户已允许删除确实没有模块的历史菜单，但不能仅因当前未关联就删除权限；仍被使用的权限须保留或迁移归属，删除动作有审计及回退映射。

### 18.4 继承与并发合同

读取同时返回有效配置及其来源、commonRevision、workspace覆盖状态和作用域修订标识；有效common修订号不能直接当作workspace写入CAS。

“恢复继承”是明确的workspace覆盖解除动作，校验预期作用域修订、权限及目标归属，与审计原子提交。解除后失效对应运行缓存，重新读取并展示实际继承来源；没有common时显示未配置，不伪造可运行配置。

不能简单删除行、再创建revision=1，否则旧请求可能再次匹配。以持久作用域版本/墓碑等方式保持修订单调，覆盖新增、修改、重置、重建全过程；冲突保留草稿，重复操作可识别。增加“旧保存延迟到达重置/重建之后”用例，验证无法恢复已经解除的旧覆盖。

### 18.5 原生层级及协议控制复杂度

可信浮层WebContentsView仍是首选验证候选，并非已确定可交付架构。Electron官方仅证明子View可调整顺序，不保证透明绘制、透明区域输入穿透或本项目原UI迁移成本；必须在锁定Electron43/macOS验证。未通过前不迁移全部抽屉，也不另建整套账户/偏好Provider。复用原UI，根控制器持有状态，浮层只接收必要投影和有限动作。

普通浮层继续遵守业务WebView不隐藏、不销毁、不重载；锁屏由主进程控制并覆盖所有归属窗口，不能只靠React状态或快捷键拦截。版本小窗仍保持原右下位置和效果。技术验证失败时保留安全门禁并记录阻塞，不默默改用隐藏方案。

F03/F04先采用最小足够的合同：请求关联、激活租约、导航代次、同代次单调状态序号及原子快照。明确各自职责，避免重复引入多个含义相同的generation。预打开事件仅有界暂存，返回后与快照按序合并；超时/取消释放本请求租约，不能关闭后续复用实例。桥接能力声明包含协议版本，旧客户端明确提示升级。状态ready仅说明当前导航加载状态，不能抹去资源注入失败告警。

### 18.6 店铺会话交付边界

通用菜单会话按菜单隔离可保留；店铺模式则引用既有会话服务的受控实例/租约，先核验真实持有方、客户端及生命周期，禁止通过复制Cookie到菜单JSON实现复用。店铺元数据已同步与当前设备已有有效登录态是两个验收条件；跨设备不能假定本地persist分区可直接复用。

common配置可定义会话策略，具体workspace店铺绑定必须属于目标工作区，不能将一个工作区的shopId推广到全部工作区。下拉主标题为店铺名或未同步，副标题为获授权可见的完整账号；运行时再次验证店铺权限和会话状态。达人广场独立封装与替换要有单独来源映射和验收，不能只修改菜单URL就记为完成。

### 18.7 新增检查与发布约束

除T01—T14、C01—C10外补充：不同workspace同模块权限映射；同权限多菜单去重选择；升级保留管理员覆盖；权威目录合法为空与接口失败的区别；覆盖重置/重建的迟到写；common不泄漏workspace绑定；会话元数据存在但设备未登录。

完整交付不能预设只执行107：先审查实际迁移台账，再追加所需数据迁移并演练106→新版本、重复初始化及应用回退。只做局部修复时不捎带无关迁移。Web/API、目录接管、原生能力及店铺模式分别设置就绪条件，避免Web已发布但安装客户端永远加载。

本次复评只更新方案及完整性清单，没有再次运行Go/Node测试、连接集群或验证最终原生GUI；已有测试结论仍仅对应原PR HEAD。
