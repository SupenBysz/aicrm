## 1. 结论及证据边界

菜单管理尚未进入当前main和线上。此前围绕PR #11列出的五项问题，属于贡献代码的正确性审查；它们修完不等于用户要求的菜单管理、导航、授权和店铺会话已经完整交付。上一版方案把部分能力写成“集成回归”，没有将缺失实现列为独立交付，范围不完整。

本轮核对：

- main为`cbf0ddd569e9e5c86ccac39e8f321822c30b4996`。
- Gitea现场读取PR #11仍open、未合并，HEAD为`4cc5a5fc2e9336ea613d129527ab51c8362bc7ca`。
- 线上认证后的`GET /api/v1/menu-directory/management`、`/workbench`均404。
- 线上角色列表200，但三个系统角色的permissionIds均为空数组；这不表示实际授权为空。main的ListRoles明确把PermissionIDs初始化为空，UI直接以该数组初始化勾选。
- 审计登录会话已注销；没有修改菜单、角色或外观。

## 3. 具体证据与复现

### 3.1 当前没有菜单管理页面

main中的`plugins/ky-access-management/src/index.tsx`与`routes.tsx`仅登记roles、permissions。PR才增加`/menu-directory`、MenuDirectoryPage及platform.menu_catalog权限，线上路由/API不具备这一批能力。

### 3.2 内部菜单配置未接入导航

PR的WorkspaceLayout仍从plugin.menus、workbenchMenus和内置数组产生内部菜单，再调用visibleWebViewGroups补充WebView。后者给buildMenuNavigation传入空candidates，动态生成逻辑只处理pageType=webview。

本轮直接执行PR原始buildMenuNavigation：向该调用方式提供一个已经改名、改图标的internal角色菜单，输出为`standalone=[]、groups=[]`。这证明当前目录投影没有接管该内部菜单；页面上看到的仍由另一套插件固定元数据产生。

### 3.3 空目录会让菜单权限不可管理

PR RolesPage以assignableMenuCodes过滤所有category=menu权限；空目录时该集合为空。107没有ky_menu_directory插入数据，贡献分支目前也不能依靠初始化脚本自动覆盖现有导航。

保存时保留hiddenExistingIds可以防止直接清空既有授权，但用户仍看不到这些权限，无法核对或撤销。必须将“不丢已有授权”和“已有授权可理解、可管理”同时验收。

### 3.4 类别及中文不能只靠旧字典兜底

PR角色授权树中的非菜单权限仍按领域/资源展示；已有Segmented用于角色状态，不等于授权窗口有四类筛选。公共label函数未命中映射时回显原字符串，因此不能声称所有英文资源名已经消除。本轮没有逐一遍历全部线上权限名称，须在后续生成完整缺失中文映射清单。

### 3.5 会话与继承缺口

MenuDirectoryPage没有shopId/sessionSource等绑定；原生sessionPartition只包含身份、workspace、directory和menu。它是新的隔离分区，不能自动获得现有店铺登录态。

配置API为读取/保存；没有解除workspace覆盖动作。已有workspace配置优先于common，故在UI切换为common或保存common都不等于恢复继承。

## 4. 补齐方式与顺序

### A. 建立完整目录与权限映射表

对每个现有模块记录：目录类型、workspace、稳定menuKey、中文名称、父级、图标、排序、内部routeKey/path、菜单权限码、页面/操作权限归属、终端支持和数据来源。

- 内置与插件路由候选来源必须是本项目受信任注册信息，不接受renderer传任意路由作为服务器事实。
- 现有平台/机构/企业可能使用不同权限码，先逐项确认映射，不能仅按相同资源前缀猜测或给所有角色补权限。
- 初始化幂等、保留管理员已有修改、保留身份/工作区隔离；必要的数据修复明确版本与审计。
- 历史条目无模块、无有效路由、无资源引用时可按用户此前要求移除，但先出真实引用核对结果；仍有效但未映射的条目必须补映射，不能误删。
- 对没有真实业务配置的达人广场菜单，不在准生产写入示例URL冒充正式配置。

### B. 统一导航与授权投影

实际导航、菜单管理树、角色授权菜单树使用同一份有效目录结构；内部/原生菜单都参与。真正的路由访问与服务端业务权限仍独立校验，改名、移动、排序不能扩大授权。

目录迁移准备完成前，整套保持旧注册表路径并禁止新目录切换，显示未就绪原因；初始化就绪状态必须与合法空结果分开。切换新权威目录后，合法空结果及停用/无授权必须生效；接口失败显示错误，不回退静态菜单复活入口。管理目录可包含无当前授权的条目，普通导航只返回用户有权的条目，两个接口职责不可混同。

多级树、排序、面包屑、未授权父级/叶子和停用祖先均有一致规则；不能把父节点显示需要和父节点授予业务权限混为一谈。

### C. 补齐表单和恢复动作

菜单表单体现真实业务字段和中文提示，按group/internal/webview类型显示有效项。恢复继承使用明确的“解除当前workspace覆盖”操作，不能通过保存common伪装；成功后失效正确的配置与运行缓存。

店铺会话复用必须使用现有服务的受控引用，核验目标workspace、店铺权限、停用状态和资源归属。店铺下拉主标题为同步到的店铺名，未同步则明确显示未同步；副标题为已获授权可见的原账号，不使用掩码代替用户选择所需信息。凭据/Cookie不进入菜单JSON或renderer通用消息。

通用隔离会话与店铺会话分别标明，不把G09隐含在普通partition实现里。若分批合入，可先交付通用目录，但不得标记达人广场替换已经完成。

### D. 原五项修复与完整验收

继续执行[PR #11修复方案](PR11菜单与WebView修复迭代方案.md)的F01—F05，并保留“不通过隐藏业务WebView解决普通浮层”的要求。新旧客户端、迁移107、启动恢复、区域状态保留和原生版本弹窗也在待交付范围；顶部亮暗按钮已单独上线不代表这些能力已上线。
